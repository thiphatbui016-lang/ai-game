### 它实际是怎么工作的

1. 在 Cascadeur 中注册 `Commands → MCP → Start Bridge`。
2. Cascadeur 主线程不断读取 `io/casc_cmd.json`。
3. 外部脚本写入类似 `{"id":1,"op":"set_frame","arg":20}` 的命令。
4. 插件调用 Cascadeur 的 `csc` Python API 修改场景，再把结果写入 `casc_resp.json`。

目前支持读取场景信息、切换帧、添加相机、修改控制器 Fix 状态、停止桥接，以及直接执行任意 Python 代码。Cascadeur 官方确实支持这种自定义命令结构和 `csc` API，所以基础方向是成立的。[项目 README](https://github.com/BYGGOLDENSTONE/cascadeur-mcp-bridge)、[Cascadeur Python 脚本文档](https://cascadeur.com/help/tools/animation_tools/python_scripting_in_cascadeur)

### 最大的问题：它不是真正的标准 MCP Server

标准 MCP 会通过 JSON-RPC 暴露 `tools/list`、`tools/call` 和参数 Schema，并使用 stdio 或 Streamable HTTP 等传输方式。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)、[MCP Transport 规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

这个项目只有自定义的 `id/op/arg` 文件协议：

- 不能直接填进 Codex、Claude Desktop 的 MCP 配置。
- 没有工具自动发现和参数 Schema。
- 还缺少一层真正的 MCP Server，把 MCP 调用转换成这些 JSON 文件。

因此更准确的名字应当是 **Cascadeur File Bridge**。

### 主要风险

- **Cascadeur 会卡死界面**：桥接运行在主线程，最长持续 240 秒，这期间软件显示“未响应”。
- **安全风险很高**：`py` 命令直接调用 `exec()`，获得的是完整 Python 权限，不仅能修改动画，也能访问和删除本机文件。[核心实现](https://github.com/BYGGOLDENSTONE/cascadeur-mcp-bridge/blob/main/mcp_commands/start_bridge.py)
- **所谓“可撤销”只对部分操作成立**：任意 Python 代码不一定进入 Cascadeur Undo 历史。
- **不支持并发和队列**：只有一个命令文件，多个请求可能互相覆盖。
- **实现有一些脆弱点**：
  - 手臂识别依赖 `clavicle/upperarm/lowerarm/hand` 字符串，而且区分大小写。
  - 错误的 preset 值不会报错，而会自动当成 `arms_free`。
  - `set_frame` 执行失败时，外层仍可能返回 `ok: true`。
  - `fix_preset` 使用的 `pycsc` 没有出现在公开 API 文档中，版本兼容风险高。
- **成熟度很低**：截至今天只有 1 次初始提交、0 Star、0 Fork、没有 Release、测试或正式驱动程序；README 只声明测试过 Windows Cascadeur 2026.1.2。[仓库状态](https://github.com/BYGGOLDENSTONE/cascadeur-mcp-bridge)

### 我的建议

**可以拿它做底座，但需要补一层。**比较合理的成品结构是：

- 外部：真正的标准 MCP Server，供 Codex/Claude 直接连接。
- 内部：保留这个文件桥接，只负责进入 Cascadeur 主线程。

- 改成白名单工具，例如：获取骨架层级、读取/设置关键帧、导入 FBX、设置控制器、运行 AutoPhysics、保存和导出。
- 加入原子写入、请求队列、超时、场景备份、危险操作确认和版本检测。
- 尝试把 240 秒阻塞循环改成短时批处理或 Cascadeur 可支持的事件调度方式。

综合评价：**概念价值 8/10，当前完成度 3/10，生产可用性 2/10。**它证明了控制路径可行，但距离“让 Codex 稳定操控 Cascadeur”还差一个正式 MCP 层和一整套安全、可靠性设计。

### 已确认的官方入口

Cascadeur 2025.3 以后，Inbetweening 已成为一种时间轴插值类型。Python API 中明确提供：

```python
csc.layers.layer.Interpolation.AI
```

并提供官方菜单动作：

```python
"Scene.Inbetween interpolation switcher"
```

官方 API 也能通过 `set_full_selection_by_parts(layer_ids, first, last)` 设置轨道和帧区间。[Inbetweening 文档](https://cascadeur.com/help/category/278)、[AI 插值枚举](https://cascadeur.com/python-api/_generate/csc.layers.layer.Interpolation.html)、[Action ID 列表](https://cascadeur.com/help/category/301)、[Timeline 选择 API](https://cascadeur.com/python-api/_generate/csc.layers.Selector.html)

因此可以给现有 bridge 增加一个 `inbetween` 操作，大致实现为：

```python
def _run_inbetween(arg):
    start = int(arg["start"])
    end = int(arg["end"])
    wanted_tracks = set(arg.get("tracks", []))

    app = _app()
    scene = _domain()
    viewer = scene.layers_viewer()

    layer_ids = [
        layer_id
        for layer_id in viewer.all_layer_ids()
        if not wanted_tracks
        or viewer.header(layer_id).name in wanted_tracks
    ]

    if not layer_ids:
        raise ValueError("No matching animation tracks")

    scene.get_layers_selector().set_full_selection_by_parts(
        layer_ids, start, end
    )

    app.get_action_manager().call_action(
        "Scene.Inbetween interpolation switcher"
    )

    return {
        "start": start,
        "end": end,
        "tracks": [
            viewer.header(layer_id).name
            for layer_id in layer_ids
        ]
    }
```

调用形式可以设计成：

```json
{
  "id": 7,
  "op": "inbetween",
  "arg": {
    "start": 0,
    "end": 48,
    "tracks": ["Body", "Legs", "Arms", "Head"]
  }
}
```

### 使用前提

Inbetweening 不是对任何 FBX/BVH 都能直接工作，场景需要满足：

- 人形角色。
- 标准 Cascadeur Rig。
- Rig 支持 AutoPosing。
- 选区里至少有两个关键帧。
- 相邻关键帧间距不能超过 120 帧；整个选区可以更长。
- 更适合走、跑、跳、格斗、杂技等地面动作。
- 暂不适合飞行、游泳、上下楼、持武器或精确双人交互。

所以对于外部 FBX/BVH，合理流程是：

`导入动作 → Quick Rig/Retarget 到 Cascadeur 标准 Rig → 设置关键姿势 → Inbetweening → Fulcrum Cleaning/AutoPhysics → 导出 FBX`

### 建议增加的安全工具

现有 bridge 最好增加四个明确操作，而不是依赖任意 `py`：

- `timeline_info`：返回轨道名称、关键帧和当前插值类型。

## ARDY 是做什么的

ARDY 是一个实时动作生成模型。简单说：

> 你输入文字、移动路线、关键帧或关节约束，它会连续生成角色动作。

它主要支持：

- 文字控制：例如“向前跑，然后转身挥手”
- 实时更换提示词，动作不中断
- 指定角色移动路径和落脚位置
- 指定某些关键帧或关节位置
- 键盘、鼠标实时控制角色移动
- 批量生成动作文件

它不是单纯做两帧之间的 Inbetweening，而是一个“可以持续生成、实时响应控制”的动作模型。论文报告使用四步扩散时平均生成延迟约 33ms，但这不能直接等同于完整网页界面或你的实际工作流延迟。

## “满血版本”应该选哪个

官方目前只有四个模型：

| 模型 | 用途 | 预测长度 |
|---|---|---:|
| [Core Horizon40](https://huggingface.co/nvidia/ARDY-Core-RP-20FPS-Horizon40) | 通用人形角色 | 40帧，约2秒 |
| [Core Horizon8](https://huggingface.co/nvidia/ARDY-Core-RP-20FPS-Horizon8) | 通用人形、强调快速响应 | 8帧，约0.4秒 |
| [G1 Horizon52](https://huggingface.co/nvidia/ARDY-G1-RP-25FPS-Horizon52) | Unitree G1机器人 | 52帧，约2.08秒 |
| [G1 Horizon8](https://huggingface.co/nvidia/ARDY-G1-RP-25FPS-Horizon8) | G1机器人、快速响应 | 8帧，约0.32秒 |

如果你的目标是人物动作、游戏角色，后续还想进入 Cascadeur：

> 建议把 `ARDY-Core-RP-20FPS-Horizon40` 当作“满血版”。

原因是它是 Core 骨架的默认模型，也是目前通用人形版本里预测范围最长的。Horizon8 不是小参数阉割版，更多是牺牲预测长度来换实时响应。

如果你做的是 Unitree G1 机器人，“满血版”则是 `G1 Horizon52`。

## 需要注意的真实情况

ARDY 目前非常新：

- GitHub 只有 `main` 分支。
- [暂时没有正式 Release](https://github.com/nv-tlabs/ardy/releases)。
- 公开内容主要是推理、Demo和预训练权重；完整训练代码目前没有看到，[社区也正在询问训练代码何时开放](https://github.com/nv-tlabs/ardy/issues/3)。
- “完整体验”不仅需要约 326M 参数的动作模型，还依赖受权限控制的 [Meta-Llama-3-8B-Instruct](https://huggingface.co/meta-llama/Meta-Llama-3-8B-Instruct) 来理解文字，所以需要 Hugging Face 账号、模型访问权限和 Token。
- 官方主要支持 Linux；目前已有 [Windows Demo 兼容问题](https://github.com/nv-tlabs/ardy/issues/4)。
- 原生输出以 NPZ 为主，没有官方直接输出 BVH/FBX；要进 Cascadeur，需要增加 NPZ → BVH/FBX 的骨架转换和重定向环节，[社区正在补相关转换工具](https://github.com/nv-tlabs/ardy/issues/5)。

结论：我们应该先测试 `Core Horizon40` 的原生精度版本，不采用量化模型；在 Linux 的 H20 上运行 ARDY，再把动作转换给 Cascadeur。这个方向比试图直接在 Cascadeur或Windows里面安装 ARDY更稳。
