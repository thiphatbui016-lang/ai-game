## 一、整体训练流程

1. **确定任务与动作协议**

   输入是游戏画面和任务指令，输出是未来 6 个、间隔约 33ms 的键鼠动作块。

2. **生成 ShareGPT 风格 JSONL 数据**

   每行包含：

   - `conversations`：human 轮放图片标记、动作规则和任务指令；gpt 轮放动作串。
   - `images`：图片绝对路径。
   - `meta.stream`：`control`、`web`、`cog/if` 等数据流。
   - `context_mode`：单帧 `non_history` 或多帧 `history`。
   - 动作格式版本等元数据。

3. **数据清洗与质检**

   检查图片存在性、`<image>` 数量、动作可解析性、坐标范围、IDLE 比例、数据流配比、任务指令位置以及数据是否真正打散。

4. **准备 YAML**

   YAML 是参数真值来源。启动脚本只在显式设置环境变量时覆盖 YAML。

5. **先跑 Smoke Test**

   建议先跑 30 步，验证数据读取、显存、梯度累积、保存和多机通信。

6. **进行 SFT/PT 训练**

   调用链是：

   ```text
   run_*.sh
      → train.sh
         → tasks/train_vlm_patched.py
         → YAML + 命令行覆盖参数
   ```

7. **按 checkpoint 做双口径评测**

   - 通用能力：OCRBench、CMMMU-val、MMBench-CN。
   - 动作能力：动作 JS 散度、解析失败率、空闲率、镜头零位、大转视角等。
   - 最后还要做在线/实机任务成功率评测。

8. **选定稳定 checkpoint 后，再考虑 KTO**

   KTO 使用 `tasks/train_vlm_kto.py`，用于动作分布塑形，不应替代 SFT/PT 基础训练。

## 二、需要什么数据

### 1. 游戏控制数据

至少需要：

- 当前游戏画面；
- 当前任务或阶段指令；
- 对应的键盘状态；
- 鼠标相对位移、滚轮和按键；
- 连续动作时间窗口；
- 可选的行为阶段、场景、角色状态等标签。

当前数据的动作串类似：

```text
<|action_start|>
0 0 0 ; W ; W ; W ; ; ;
<|action_end|>
```

分号分隔 6 个动作块。

### 2. 推荐的鼠标表示

早期采用 `move/cursor` 双模式：

- `move X Y Z`：相对位移；
- `cursor X Y Z`：绝对位置。

实际出现了严重的绝对坐标塌缩和坐标系不一致。v0011 起改为：

- 裸 `X Y Z` 相对位移；
- 点击用 `LMB/RMB` token，不再带绝对坐标；
- deadzone `τ=4`。

如果启动新实验，我会优先使用这种 xyz 相对位移方案，但评测时必须和同编码模型比较，不能跨编码直接比较 JS 散度。

### 3. 防遗忘数据

不能只用游戏动作数据。仓库里的“纯 VLA SFT、无 web”对照结果是：

- OCRBench：`0.0`
- MMBench-CN：`0.0067`

说明通用视觉语言能力几乎完全丢失。

建议按 token 配比控制在大致：

- control：约 77%
- web：约 22%
- cog/IF：约 1%

注意这是 token 口径，不是行数口径。web 样本通常文本更长，行数占比可能达到 35%–40%。

### 4. IDLE 数据

IDLE 不能删得过少，也不能删得太狠：

- 过多：模型倾向什么都不做；
- 过少：模型持续乱转、乱按。

训练数据清洗文档使用的同口径锚值约为 `6.03%`；离线 2500 帧真人 GT 的空闲率是 `1.08%`。两个数字口径不同，不应混用。正确做法是：

- 只删除真正 idle；
- 动作帧全部保留；
- 用同一采样口径确定训练集目标；
- 在固定未见集上另外评估模型空闲率。

### 5. History 数据

History 版本使用约 20 帧、40 轮对话，需要：

- 连续帧；
- 每帧对应动作；
- 正确的图片—动作顺序；
- 20k–32k 上下文；
- 更小的 micro batch；
- 必要时启用 Ulysses 序列并行。

建议先把单帧模型做稳定，再引入 history，否则很难判断问题来自时序、数据还是视觉塔漂移。

## 三、建议的起步参数

| 参数 | 推荐起点 | 说明 |
|---|---:|---|
| 基座 | Qwen3-VL-4B-Instruct | 仓库统一基座 |
| `freeze_vit` | `true` | 最重要的安全项 |
| `max_seq_len` | `4096` | 单帧足够 |
| `global_batch_size` | `128` 或 `256` | 小规模实验先 128；大数据/16 卡可用 256 |
| `micro_batch_size` | 按显存设，一般 4–8 | 通过 Smoke Test 决定 |
| 学习率 | GBS128：`1e-5`；GBS256：`1.4e-5` | 仓库中较稳定的组合 |
| 调度 | `cosine` | v0016 单变量实验略优于 constant |
| warmup | `0.05` | 全项目固定 |
| `lr_min` | `1e-7` | cosine 最低点 |
| epoch | 先跑 2，逐 epoch 评测 | 不建议盲目增加 |
| `max_grad_norm` | `1.0` | 固定设置 |
| `weight_decay` | `0` | 当前项目固定 |
| seed | `42` | 保持可复现 |
| 精度/并行 | FSDP2、bf16、full shard | 当前标准配置 |
| AdamW β2 | `0.999` | 源码补丁，不在 YAML 内 |
| 动态 batch | 新实验优先 `false` | 按行数计步更清晰 |

梯度累积计算：

```text
gradient_accumulation
= global_batch_size ÷ (data_parallel_size × micro_batch_size)
```

例如 16 卡、每卡 micro batch 8、GBS 256，则累积 2 步。

特别注意：

- `load_path: auto` 会从同一输出目录自动续训；
- 新实验必须使用唯一 `RUN_NAME/output_dir`，或者明确设置 `load_path: null`；
- 文件名可能与 YAML 实际字段不一致，必须看 YAML 内容；
- `freeze_vit: true` 时，`vit_lr` 只是死值；
- `dyn_bsz: true` 按 token 预算计步，`false` 按行数计步，不能混算。

## 五、如何一步步改进效果

### 第一步：先建立可信基线

建议从下面组合起步：

- 单帧；
- xyz 相对鼠标编码；
- 冻结 ViT；
- 4k 上下文；
- control/web/cog 混合；
- GBS128 + LR `1e-5`，或者 GBS256 + LR `1.4e-5`；
- cosine；
- 2 epoch；
- 每个 epoch 保存并评测。

不要一开始同时改数据、编码、学习率和视觉塔。

### 第二步：优先解决数据问题

每次训练前固定做这些 GATE：

- JSONL 可逐行解析；
- 所有图片存在；
- `<image>` 数与图片数一致；
- gpt 动作串解析失败为 0；
- 坐标范围合法；
- cursor/xyz 语义与提示词一致；
- control/web/cog 配比符合预期；
- IDLE 使用同一判定逻辑；
- 数据真正全局打散；
- 单轮、多轮数据血缘没有混错。

仓库中多数事故都属于这一层，而不是模型结构问题。

### 第三步：用单变量实验改动作能力

建议顺序：

1. 固定行集，只比较动作编码；
2. 固定编码，只调整 IDLE；
3. 固定上述两项，只加入 HITL 纠偏；
4. 固定 control，只调整 web/cog 比例；
5. 最后再调整学习率、batch 和 epoch。

v0012 就是很好的设计：与旧数据几乎完全同源，只改鼠标编码，最终镜头零位 `49.80%`，非常接近真人 GT `49.68%`。

### 第四步：每个 epoch 都做双口径评测

仓库里没有一个版本同时做到“通用能力最好、动作最好、格式最好”：

- V0017 通用能力最佳，但动作侧偏弱；
- v0013 ep1 动作分布最好，但通用能力已经明显塌陷；
- v0003 ep3 是双模编码里较稳的甜点；
- v0016 ep2 是 xyz 线中相对稳定的点；
- v0003 ep4 以后解析失败迅速增加，ep6 达到 `86.5%`。

因此选模型要看：

```text
格式合法
  ∩ 通用视觉语言能力未明显退化
  ∩ 动作分布合理
  ∩ 实机任务成功率提升
```

不能用训练 loss 最低直接选最终模型。

### 第五步：单帧稳定后再做 History

History 会同时改变：

- 序列长度；
- micro batch；
- 并行策略；
- 数据结构；
- 离线评测口径。

如果要做，建议只改变 history 这一项，其余沿用已验证的单帧基线；并建立专门的时序评测，不能继续用单帧指标直接排名。

### 第六步：最后再上 KTO

KTO 建议：

- 使用格式干净的 SFT checkpoint，例如类似 v0003 ep3，而不是已经有格式病的 ep4；
- LR 从 `5e-7` 或 `1e-6` 开始；
- 小步数逐段评测；
- 同时监控动作塑形和解析失败率。

现有结果中，KTO gs60 把镜头大转从 `14.6%` 拉到 `24.6%`，接近真人 `25.56%`，但解析失败率也从 `13.8%` 上升到 `19%`。说明 KTO 有效，但会放大基底已有的格式问题。

我重点核对的文档是：[VLA 总览](https://ezone.kingsoft.com/code/game-ai/chenkai_airepo/-/blob/master/VLA%2FREADME.md)、[实验演进索引](https://ezone.kingsoft.com/code/game-ai/chenkai_airepo/-/blob/master/VLA%2Fdocs%2FREADME.md)、[数据集说明](https://ezone.kingsoft.com/code/game-ai/chenkai_airepo/-/blob/master/VLA%2Fdataset%2F数据集说明.html)、[训练配置说明](https://ezone.kingsoft.com/code/game-ai/chenkai_airepo/-/blob/master/VLA%2Fconfigs%2F训练配置说明.html)和[离线评测汇总](https://ezone.kingsoft.com/code/game-ai/chenkai_airepo/-/blob/master/VLA%2Fevals%2FJX3-VLA%20离线评测汇总.md)。

## 15. Codex

我再核对一下仓库里是否记录了推理延迟或端到端实测值。这里要区分三个数字：模型计算耗时、输入画面到首个动作的端到端延迟，以及一次输出覆盖的动作时长。

## 16. Codex

目前仓库**没有记录实测的“画面进入 → 动作输出”端到端延迟**，所以不能直接说当前响应是 100ms 或 200ms。

文档中明确的 `200ms` 是动作规划窗口，不是推理耗时：

```text
一次输出规划未来约 200ms
= 6 个动作步 × 33ms
≈ 198ms
```

也就是说，模型看到一张画面后，一次生成接下来约 200ms 的操作序列。但生成这段动作本身花多久，文档没有测速结果。[数据样本说明](https://ezone.kingsoft.com/code/game-ai/chenkai_airepo/-/blob/master/VLA%2Fdataset%2F数据集说明.html)

真正的响应时间应该这样计算：

```text
端到端延迟
= 截图/采集
+ 图像预处理与传输
+ 视觉编码
+ 动作 token 生成
+ 格式解析
+ 键鼠指令下发
```

另外，YAML 中的 `fps: 2.0` 是训练时的视频采样配置，也不代表线上每秒只能响应两次。

工程上我建议：

- **目标值：≤100ms**，能给 200ms 动作窗口留下充足余量。
- **可接受：100–150ms**。
- **风险区：150–200ms**，动作开始时画面已经较旧。
- **不可接受：>200ms**，模型还没算完，上一批动作就执行完了，控制会出现空档或明显滞后。

如果是单张 H20/H100、Qwen3-VL-4B、单帧 4k 上下文、短动作输出，粗略工程预估可能在 **80–200ms 端到端**，但这不是当前系统实测值，部署方式、图片分辨率和推理引擎都会造成很大差异。

最应该补的是下面五个时间戳，并统计至少 500 次的 P50/P95：

```text
T0：画面截取完成
T1：服务收到请求
T2：视觉编码完成
T3：首个动作 token 产生
T4：完整动作串产生
T5：第一个键鼠动作真正执行
```

重点看：

```text
首动作响应 = T5 - T0
完整生成延迟 = T4 - T0
动作执行时的画面年龄 = 当前时间 - 画面采集时间
```

其中最关键的不是“完整 6 步什么时候生成完”，而是**第一个可执行动作多久能出来**。如果推理支持流式解析，可以首个动作生成后立即执行，后面的动作继续生成，从而显著降低体感延迟。
